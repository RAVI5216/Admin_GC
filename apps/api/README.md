# SmartBin Backend

The website backend is the Socket.IO relay between the dedicated EC2 SmartBin service and the React dashboard. It owns the website REST API, DynamoDB-backed authentication, profiles, employers, reports, tasks, notifications, and the browser-facing Socket.IO server.

## Architecture

```text
ESP32 -> MQTT -> AWS IoT Core -> MQTT -> EC2 SmartBin IoT Service
      -> Socket.IO (smartbin-data) -> Website Backend
      -> Socket.IO (smartbin-data) -> React Frontend
```

AWS IoT/MQTT is handled only by the EC2 SmartBin IoT Service. This backend does not connect to AWS IoT or subscribe to MQTT, and the React frontend never connects to AWS IoT or EC2 directly.

## Environment

Create `smartbin-backend/.env` (it is ignored by Git):

```env
PORT=5000
AWS_REGION=ap-southeast-2
SMARTBIN_IOT_SERVICE_URL=http://54.206.16.121
SMTP_HOST=smtp.gmail.com
SMTP_PORT=587
SMTP_USER=<your Gmail address>
SMTP_PASSWORD=<your Gmail app password>
SMTP_FROM=<your Gmail address>
```

Admin account seeding, when required, uses `ADMIN_EMAIL`, `ADMIN_NAME`, and `ADMIN_PASSWORD` temporarily in the backend environment. The seed command hashes the password with bcrypt and stores only the hash in DynamoDB; do not commit these values.

The frontend's `smartbin-frontend/.env.local` is also ignored by Git and should contain:

```env
VITE_API_URL=http://localhost:5000
```

## SmartBin data flow

`SmartBinIoTService` connects to `SMARTBIN_IOT_SERVICE_URL` through Socket.IO at `/socket.io`. It validates each incoming `smartbin-data` event and broadcasts the validated event to website clients using the same event name. The client automatically reconnects when EC2 is temporarily unavailable; the Express server continues serving REST requests.

Expected sensor fields are `deviceId`, `fillPercentage`, `distance`, `uptime`, `status`, `online`, and `lastUpdated`.

Sensor events are not automatically stored as historical records on every message. Historical IoT storage is a separate future feature. Existing alert-notification behavior remains independent of raw sensor-event storage.

## Run

```bash
cd smartbin-backend
npm install
npm start
```

The backend listens on port 5000 by default. Useful endpoints include `GET /`, `GET /health`, `GET /profile`, `GET /notifications`, `POST /notifications`, `PUT /notifications/:id`, `GET /reports`, `PATCH /reports/:reportId/status`, `POST /auth/login`, `POST /auth/verify-login-otp`, `POST /auth/forgot-password`, `POST /auth/reset-password`, `GET /api/employers`, and `POST /api/tasks`.

`GarbageGuardianDashAdmin` is the single-table store for admin accounts, their dashboard profile attributes, and notifications. Its String partition key is `email`. Admin items use the actual admin email as the key and `recordType: "admin"`; the admin password is stored only as a bcrypt `passwordHash`. Notification items use `email: "NOTIFICATION#<id>"`, `recordType: "notification"`, and a `notificationId`; the API maps that identifier back to its existing `_id` response field. The profile is held on the designated admin item, not in another table. The backend role needs `dynamodb:GetItem`, `dynamodb:PutItem`, `dynamodb:UpdateItem`, `dynamodb:DeleteItem`, `dynamodb:Scan`, and `dynamodb:TransactWriteItems` on `GarbageGuardianDashAdmin`.

`GET /reports` reads the existing `GarbageGuardianReports` DynamoDB table in `ap-southeast-2`. The backend runtime identity must have `dynamodb:Scan` permission for that table. Configure AWS credentials through the standard AWS SDK credential provider chain (for example, an IAM role in AWS or a local AWS CLI profile); do not put AWS access keys in the `.env` file. The endpoint returns report items as stored, and the admin page renders their attributes dynamically.

`GET /api/employers` scans the existing `GarbageGuardianUsers` DynamoDB table and includes an item if any of these match: `employeeId` starts with `EMP-` (case-insensitive), `role` equals `employee` after trimming and lowercasing, or `userId` starts with `EMP-` (case-insensitive). `POST /api/employers/ids` generates distinct User ID and Employee ID values in the `EMP-{epoch-milliseconds}` format (for example, `EMP-1791108656511`) and checks them against existing `userId` and `employeeId` values in that table. `POST /api/employers` rechecks both values before adding the user to the same table with `userId`, `employeeId`, `name`, `email`, `role`, `createdAt`, and optional `phone` and `department` attributes. The IDs are generated by the backend and are read-only in the form; the other fields are entered manually. The backend hashes the required initial password as `passwordHash` and rejects IDs that already exist. The response includes actual user attributes except password-, secret-, token-, credential-, OTP-, and reset-code fields. The backend runtime identity needs `dynamodb:Scan` and `dynamodb:PutItem` permissions for this table. The Employers roster displays the returned user attributes; it does not create a separate employers table. The API derives `employerId` as `EMP-{userId}` for display only; this value is not written to DynamoDB and the original `userId` remains unchanged.

The Assign action loads the existing `GET /reports` results in the employer dialog with report ID, location, creation time, bin ID, issue type, and status. Assigning one report posts `assignedUserId` and `reportId` to `POST /api/tasks`. The backend verifies that the selected user is an employee in `GarbageGuardianUsers`, reads the report from `GarbageGuardianReports`, then uses one DynamoDB transaction to create a task in `GarbageGuardianTasks` and set the existing report's `status` attribute to `assigned`. The task uses `taskID` (generated UUID string, the table partition key), `assignedUserId` (the original `GarbageGuardianUsers.userId`), `reportId`, a task name derived from issue type and report ID, a description derived from report details, `status` (`assigned`), and `createdAt` (ISO timestamp).

The Reports page also provides an Unassign action for assigned reports using `PATCH /reports/:reportId/status` with `{"status":"unassigned"}`. The backend scans existing task items for that report and transactionally changes the report and all linked tasks from `assigned` to `unassigned`. The scan is paginated; the DynamoDB transaction is rejected rather than partially applied if there are more than 99 linked tasks. This action needs `dynamodb:GetItem` on `GarbageGuardianUsers` and `GarbageGuardianReports`, `dynamodb:Scan` on `GarbageGuardianTasks`, and `dynamodb:TransactWriteItems` on `GarbageGuardianReports` and `GarbageGuardianTasks`. No new table is created. The dashboard's existing protected route still gates the UI; the backend currently has no session/token middleware on its REST APIs.

Admin sign-in requires the account password followed by a six-digit email code. `POST /auth/login` sends a code to the registered admin email after validating the password; `POST /auth/verify-login-otp` verifies it before the frontend completes sign-in. Login codes are hashed in `GarbageGuardianDashAdmin`, expire after 10 minutes, are single-use, are limited to five verification attempts, and have a 60-second resend cooldown. Admin password recovery uses `POST /auth/forgot-password` to email a separate six-digit code and `POST /auth/reset-password` to verify it and update `GarbageGuardianDashAdmin.passwordHash`. Configure Gmail SMTP with an app password in the backend `.env`; never use or commit your regular Gmail password.

Existing admin accounts, dashboard profile data, and notifications were copied from MongoDB into `GarbageGuardianDashAdmin`. The MongoDB source data was not deleted. MongoDB is no longer required by the backend, and the `mongodb` package and connection code have been removed.
